# 0001. Run the project with an Orchestrator and lanes

Date: {{DATE}}. Status: proposed (the CTO sets it to accepted once the user confirms README §Operating decisions).

## Context

The project is bigger than one session can hold. We want one Orchestrator session coordinating child sessions, each doing one ticket, on top of the `mattpocock-skills` ticket flow (wayfinder, to-spec, to-tickets, implement, retro).

## Decision

Use three levels: Workflow (1 ticket, [workflow.md](../agents/workflow.md)), Board (Orchestrator + lanes, [docs/orchestration/](../orchestration/README.md)), Roadmap ([phases.md](../orchestration/phases.md)). Rules from the lane-board plugin ({{SOURCE}}): the Orchestrator never does a lane's work, a lane starts only on the user's words, the title is the status, a table of stop points, reports by session id, handover with "Open lanes", one merge at a time.

The Orchestrator writes the shared tracker state (claims, Decisions-so-far, new tickets); a lane writes only its own ticket file. Reason: lanes run in separate worktrees, and several lanes editing `map.md` would conflict on merge.

## Consequences

- Deliberately differs from the `wayfinder` skill, where the session resolving a ticket writes the map.
- The user must click to start lanes: `start_session` is refused on automated turns.
- Skills marked `disable-model-invocation` (`wayfinder`, `to-spec`, `to-tickets`, `implement`, `retro`) must be typed by the user inside the lane: lanes stop with `CHECK` and give the exact command.
